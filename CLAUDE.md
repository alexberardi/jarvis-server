# jarvis-server

Single-binary Go rewrite of the Jarvis server stack.

**Start every session by reading `docs/STATUS.md`**, which says where we are and what's next. Then read the relevant sections of `docs/PLAN.md`.

## Rules

- **`docs/STATUS.md` is current state only:** the phase, the open checklist and the "Next" line. Edit it when an item is ticked, added or the plan changes, not for every PR. **No session log**: what changed and why goes in the commit message and PR description (`git log`, `gh pr list --state merged`). The old log is in `docs/status/archive-2026-10.md`.
- **Decisions get a file each** in `docs/decisions/` (`YYYY-MM-DD-<slug>.md`, format in its README): every user answer or design choice a later reader would otherwise rediscover. New files never conflict across parallel branches.
- **Go toolchain:** `mise exec go@1.27 -- go …`.
- **`CGO_ENABLED=0` always.** Native libraries (sherpa-onnx, onnxruntime) are loaded via purego (PLAN §3.4).
- **TDD** per the umbrella repo's RULES.md. Before committing, run `CGO_ENABLED=1 go test -race ./...`. The race detector needs cgo; that is test-only. Builds stay `CGO_ENABLED=0`.
- **Native libs:** run `scripts/fetch-sherpa-libs.sh` once, and `scripts/fetch-test-models.sh` for the voice integration tests (`JARVIS_SHERPA_MODELS=$PWD/.models`).
- **Behaviour parity is proven by the contract suite (`contract/`) and golden fixtures (`fixtures/golden/`), not by reading code.** A contract test is only valid once it passes against the legacy Python stack.
- **Don't port what's on the cut lists** (PLAN §7, Appendices A and B).
- **Prod** (`<user>@<prod-host>`) is **read-only** unless the user explicitly says otherwise.
- **Host placeholders** (`<prod-host>`, `<mbp-host>`, `<dev-box>`, `<dev-node>.local`, `<pi4-node>`, `<pi5-node>.local`, `<lan-subnet>`, `<user>@…`) appear throughout CLAUDE.md and `docs/`. Real values are in HOSTS.local.md (gitignored, local only).
- **Merging (user, 2026-10-14).** An agent may squash-merge **its own** PR into `main` once every required CI check has passed, then must check main's CI after the merge. **Hold for the user's review** instead, with a note saying why, when the PR:
  - changes **the access rules themselves**: the admin gateway's tier table (`internal/modules/admin/tiers.go`, `m.handle` registrations) or its expectations in `tiers_test.go` / `tiers_e2e_test.go`, authentication or authorization code (`internal/modules/auth`, `internal/platform/authn`, a module's membership/role checks), node/app credentials, or pairing approval;
  - changes release signing, update verification or the root update helper (minisign, `internal/update`, the prestart helper, `.github/workflows/release.yml`);
  - touches prod or anything that runs there outside a release;
  - weakens or removes a test or CI check to get green;
  - is marked "needs review" by its author.

  **Access tests are the gate for everything else (user, 2026-10-14).** CI's race suite includes `TestEveryAPIRouteHasATier` (every `/api` route × anonymous, member, power user, household admin, superuser, another household's member; an unclassified route fails), `TestNoMemberReachesInstallWideRoutes` and `TestMemberTiersEndToEnd`. A PR that only *uses* the access rules (UI that hides or shows pages by role, a new page behind an existing tier, client-side auth handling) may merge on green as long as it doesn't edit those tests' expectations. Any edit that loosens an expectation, or adds a route at a lower tier than `superuser`, is a change to the access rules and waits for review. A new `/api` route must be added to the expectations in the same PR (the test fails otherwise), so adding one always gets a review.

  Never merge someone else's PR (contributors, Dependabot outside the dependency rules, other agents' open PRs), and never force-push to `main`. Doc-only and test-only PRs follow the normal rule. When unsure which side a PR falls on, hold it.

## Harness (verify without the user)

- `scripts/sandbox up [--name N]`: a seeded jarvisd for this checkout on its own ports and data. Its model is the installed jarvisd's live one, through that instance's LLM API (no extra VRAM); that needs an app client in `~/.config/jarvis-harness/installed.env` (`INSTALLED_APP_ID`, `INSTALLED_APP_KEY`, created once by the user in the installed admin). `INSTALLED_LLM_URL` and `INSTALLED_LLM_LABEL=background` there (or in another file named by `JARVIS_HARNESS_ENV`) point it at another jarvisd's background label instead; the loop's verify uses prod's that way. `source .sandbox/<name>/sandbox.env` for URLs and credentials. Use a unique `--name` per agent; `down --purge` when done. Its pushes go to a fake relay that records them (`tools/fakerelay`, `$SBX_FAKERELAY/control/pushes`; `--relay none|URL` otherwise). A fresh worktree needs `scripts/fetch-sherpa-libs.sh` first.
- `go run ./tools/pipeline say -v "…" "…"`: a text conversation as the seeded node (speaker = the seeded superuser, devices from `tools/pipeline/homes/avery.json`). `… run [--filter RE] [--repeat N]` plays `tools/pipeline/scenarios/`. Every model call (prompt, tools, reply) is in `.sandbox/<name>/llm.jsonl`.
- Scripted model for UI tests: `scripts/sandbox up --llm scripted` answers from `e2e/llm/*.json` (`tools/scriptllm`; switch scripts at `$SBX_SCRIPTLLM/control/script`), no installed jarvisd needed. Format and API: `docs/decisions/2026-10-17-scripted-llm.md`; its scenarios are `e2e/llm/scenarios/`.
- Voice loop: `scripts/sandbox up --voice` adds real TTS + CPU whisper (models cached in `~/.cache/jarvis-harness`); `pipeline say|run --voice [--voice-name V]` speaks each turn, transcribes it as a node would and sends what was heard, printing `heard:`. Voice scenarios: `tools/pipeline/scenarios/voice.json` (`heard`, `max_wer` expectations).
- SIP lane (phone over SIP, L1): `scripts/sandbox up --voice --sip` adds Asterisk 22 configured like FreePBX 17 in Docker with baresip/SIPp far ends (`test/sip/`, `scripts/sip-lane`); `go run ./tools/siplane --sandbox N` plays its scenarios and checks what each far end heard (max WER). Never a real PBX or carrier (`docs/cc/phone-sip.md` §5). L2: `scripts/freepbx-lane` (a real FreePBX 17 in a qemu VM, dev box only, weekly) diffs extension 100 against L1 with `go run ./tools/siplane drift`.
- `scripts/e2e [web|mobile|all] [--filter RE] [--keep]`: the E2E regression suites against sandboxes it brings up itself (rich + scripted model, and an empty one for first-run setup) and purges after; `.e2e/<run>/report.md` + `report.json` (per test: status, time, failure screenshot, trace, console errors); exits 1 on any failure. Web suite: Playwright Test in `e2e/web/`; mobile suite: the Maestro flows of jarvis-node-mobile's `.maestro/` on mobile-shot's headless emulator (`--mobile-repo PATH` for a branch) (`docs/dev/e2e.md`). **A new admin page or mobile screen needs an entry in `e2e/coverage.json`** (its specs/flows, or why it has none); CI's `web/admin/src/coverage.test.tsx` and the mobile suite fail otherwise. `scripts/e2e voice [--llm scripted] [--audio wav|pipewire|pi]` (not in `all`): the real `jarvis-agent --profile pi` hears TTS (`e2e/voice/cases.json`, `tools/voicelane`) and its spoken reply is transcribed and checked; WAV files or a private PipeWire, never the user's audio. `--audio pi --pi-host <user>@<pi4-node>` runs it on the real Pi in the room, overnight only, and leaves the Pi as found. `scripts/e2e ios --sandbox-env FILE` (not in `all`; on a Mac with Xcode): the same Maestro flows on the harness's own iOS Simulator (`jarvis-harness-e2e`, erased per run; never the user's simulators), against a sandbox up with `scripts/sandbox up --lan` on the Mac (its `sandbox-lan.env`; a dev-box one needs its ports opened in ufw) (`docs/decisions/2026-10-18-e2e-ios-lane.md`). `scripts/sandbox up --profile empty` alone gives an install whose setup is still to do (`SBX_SETUP_TOKEN`). `scripts/sandbox node-sim --name N` pairs a simulated node (the real agent, headless) and prints its code to approve.
- `scripts/screenshots --sandbox N [--tiles 1600]`: admin SPA at phone/tablet/desktop × light/dark, with overflow and console reports (`docs/dev/screenshots.md`). UI work in `web/admin/` also loads the design skills and runs Impeccable's audit before its PR (`web/admin/CLAUDE.md`).
- `scripts/desktop-shot [--sandbox N | --offline]`: the desktop agent's island (every state) and status icon in a disposable headless sway (own XDG_RUNTIME_DIR, session bus and HOME; never the user's screen or tray), dark and light, cropped PNGs + the tray menu as text (`docs/dev/desktop-shots.md`). Needs sway: `sudo pacman -S sway` or `scripts/desktop-shot deps` (builds it into ~/.cache, no sudo).
- `scripts/mobile-shot --sandbox N [--font-scale 1.0,1.3] [--keep]`: the mobile app runs in a disposable headless emulator, logged in to the sandbox through adb reverse. The APK is a release build from a `git archive` of jarvis-node-mobile, cached in ~/.cache. The emulator uses its own AVD, `jarvis-harness`, under ~/.cache and never touches `emulator-5554`. It shoots every main screen in light and dark as a PNG, a uiautomator XML dump and `index.json`, and does one chat round trip. Exits 1 on a failure (`docs/dev/mobile-shots.md`).
- `scripts/check` before committing; `scripts/installed status` shows who holds the GPU. The installed model has one slot: sandbox calls wait behind the house's.
- Branches: harness work uses `harness/*`; subagent worktrees live in `.claude/worktrees/`.
- **Agent loop** (being built): the harness is what a pipeline of agents uses to verify its own work. The pipeline lives in the private repo `alexberardi/jarvis-loop` (checkout `~/jarvis/jarvis-loop`): `loopd` keeps the work items and runs agents through triage → build → review (a different agent) → land, with the user answering questions and approving held merges in Slack. Merge gates: agent review that judges test coverage, harness verification with screenshots in the PR, and CI, plus the hold list above. Summary in `docs/dev/agent-loop.md`; the design is `docs/DESIGN.md` there.

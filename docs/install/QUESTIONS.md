ID2, …), then fold it into [`00-installers.md`](00-installers.md). Technical choices that need no product
call are already made in the spec: release asset names and checksum verification (§4.1), the systemd unit
body (§2.1), the launchd plist keys (§2.2), PowerShell 5.1 constraints (§2.3), the upgrade sequence (§4.2),
the doctor `--fix` mechanics (§6.1), and no GPU/model prefetch (§6.2, settled by LD3).

**Already decided upstream, and not re-asked here:**

- **PLAN §3.4.** One file per OS, `CGO_ENABLED=0`, install scripts for systemd/launchd and Windows.
- **D9.** The admin SPA is embedded on 7710; the first-run wizard lives there (admin AQ3).
- **LD3.** No automatic model download.
- **LD5.** The prod cutover's models and LLM settings start clean, through the same first-run path.
- **Decision log 2026-10-06.** One RS256 key generated by jarvisd on first run, stored in the DB.
- **Admin AQ2, AQ5, AQ6** (setup token, updates, Twilio as secret settings) are asked in
  `docs/admin/QUESTIONS.md`; this spec assumes their recommendations and points at them.

## Queue

### IQ1 [scope] Service account and data directory per OS

**Context.**

jarvisd defaults its data to `~/.jarvis` (`internal/platform/config/config.go:76-82`). The legacy stack
owns the same directory (`~/.jarvis/compose`, `tokens.env`, `admin.json`, 150 GB of `.models/` on prod),
plus `/var/lib/jarvis` (compose-export default) and, on prod, a login user called `jarvis`. Nothing clashes
file-by-file today, but a legacy reset (`rm -rf ~/.jarvis`) would delete jarvisd's DB, and a jarvisd
`--purge` would delete legacy models. The dev box already runs jarvisd from `~/.jarvisd` for this reason.

The account decides:

- whether install needs sudo/admin (the firewall fix needs it once anyway);
- whether jarvisd runs before anyone logs in (a Mac mini or a desktop after a power cut);
- GPU access (`video`/`render` groups on Linux; session 0 on Windows);
- macOS Local Network privacy: LaunchAgents are subject to it (mDNS can silently fail), launchd daemons
  are exempt (Apple TN3179; verify in I0);
- how exposed the user's home (SSH keys, browser profiles) is if the LAN-facing server is compromised.

**Options.**

- **(a) A dedicated service identity**, everything named `jarvisd`:
  - Linux: system unit, system user `jarvisd` (in `video`/`render`), data `/var/lib/jarvisd`, binary
    `/usr/local/bin/jarvisd`, hardened unit (`ProtectSystem=strict`, `ProtectHome=yes`).
  - macOS: LaunchDaemon with `UserName` = the installing user, data `~/.jarvisd` (a hidden role user buys
    little on a personal Mac).
  - Windows: SCM service under the virtual account `NT SERVICE\jarvisd`, data `%ProgramData%\jarvisd`.
- **(b) Always the installing user**, data `~/.jarvisd`: a Linux system unit with `User=$SUDO_USER`,
  macOS as in (a), a Windows service running as the user (needs their password) or a logon task.
- **(c) User-level supervisors only**: systemd `--user` + linger, LaunchAgent, logon task. No admin rights
  at install, but nothing runs before logon on macOS/Windows and mDNS is at risk on macOS.

In every option: rename everything `jarvisd` (unit, label, paths, user) and change the code default from
`~/.jarvis` to `~/.jarvisd`, so jarvisd and the legacy stack can never delete each other's data.

**Recommendation: (a), with (c)'s Linux `--user` mode as an installer flag, and the rename.**

- It runs at boot on every OS, with the least privilege.
- `/var/lib/jarvisd` survives user changes and is what a sysadmin expects; models stay manageable
  through the admin's Models page, so nobody needs to browse the directory.
- The `--user` flag covers boxes without sudo and developers.

### IQ2 [scope] Windows: SCM service (needs `svc` support in Go) or a scheduled task?

**Context.**

A real Windows service must answer the Service Control Manager, so jarvisd needs a small amount of Go:
`svc.IsWindowsService()`, `svc.Run` mapping Stop/Shutdown to the existing context cancel
(`cmd/jarvisd/main.go:280`), and file logging (stderr goes nowhere under SCM). `golang.org/x/sys` is
already a dependency. Registration uses `svc/mgr` from `jarvisd service install`.

Services run in **session 0**. CUDA compute generally works there; Vulkan is less certain. A scheduled
task "at logon" runs in the user's session, where the GPU certainly works, but only after logon, and
`schtasks /end` kills rather than stops (no engine drain), which matters for upgrades.

Under any service account `os.UserHomeDir()` is a system profile (LocalSystem:
`C:\Windows\System32\config\systemprofile`), so the service must pass `--home %ProgramData%\jarvisd`.

**Options.**

- **(a) An SCM service** under `NT SERVICE\jarvisd`: automatic (delayed) start, recovery actions, clean
  stop for upgrades.
- **(b) A scheduled task at logon** for the installing user: no Go change.
- **(c) (a), with the installer falling back to (b)** on boxes where the first GPU check fails.

**Recommendation: (a), confirmed by the I0 spike (llama-server on CUDA and Vulkan in session 0).** If CUDA
fails in session 0, switch to (b) rather than carrying both paths in (c).

### IQ3 [behaviour] Thin installers: jarvisd generates every secret and owns service registration?

**Context.**

The legacy tools put the logic in shell: `./jarvis init` generated eight hex tokens and an RSA key with
`openssl` (its `base64 -w 0` is GNU-only and breaks on macOS, `jarvis:551-553`), stamped them into a dozen
`.env` files, and the admin installer wrote unit files and plists from heredocs. None of it was tested on
every OS.

jarvisd already generates its signing key on first start (`internal/modules/auth/keys.go:35-70`). Every
other admin secret is closed-when-unset (IQ4). What remains for a fresh install is the setup token (admin
AQ2) and jarvisd's own app client for job callbacks (`internal/modules/ocr/jobs.go:403-406`), both of
which jarvisd can make itself.

**Options.**

- **(a) Thin scripts, logic in Go.**
  - The scripts detect, download, verify, place the binary, then call `jarvisd service install`, which
    writes the unit / plist / SCM entry in Go.
  - jarvisd generates every secret on first start, in its DB or home at 0600.
  - jarvisd reads its own `jarvisd.env` (for unset variables), so a service and a shell `jarvisd doctor`
    see the same config; the service definition carries only `--home`.
- **(b) Fat scripts**, as `./jarvis init` did: the scripts generate tokens and write the supervisor
  files.

**Recommendation: (a).** The same binary behaves identically by hand, as a service, in CI and in a
container; service registration gets tested on the four CI runners; a reinstall can never rotate a key by
accident; each script stays around 150 lines.

### IQ4 [behaviour] Legacy admin tokens on a fresh install

**Context.**

`JARVIS_AUTH_ADMIN_TOKEN` (auth `/admin/*`), `JARVIS_CONFIG_ADMIN_TOKEN` (registry writes) and
`ADMIN_API_KEY` (cc and notifications admin routes) all fail closed when unset
(`internal/modules/auth/auth.go:80`, `internal/modules/config/config.go:519-521`,
`internal/platform/authn/principal.go:75-78`). After the admin gateway (admin AQ1) the browser never needs
them. Their remaining users are scripts: install-e2e, registering the recipes add-on, jarvis-mcp.

**Options.**

- **(a) Unset by default.** `jarvisd admin-token create <auth|config|cc>` generates one and writes it to
  `jarvisd.env` (then restart) for whoever needs it; the Connections page (admin AQ7) covers the
  recipes add-on without any token.
- **(b) Generated on first start** into the DB and shown (once) in the admin.
- **(c) Generated by the installer** into the env file, as `./jarvis init` did.

**Recommendation: (a).** Closed is the safe default, nothing a normal user does needs them, and it keeps
the installer free of secrets (IQ3).

### IQ5 [behaviour] Firewall: should the installer apply the fix?

**Context.**

STATUS install-UX finding 1: a host firewall silently blocks nodes and phones (Docker used to punch the
holes). `jarvisd doctor` detects it for ufw, firewalld, the macOS application firewall and Windows
Defender Firewall and prints the exact command (`internal/doctor/firewall.go`). Applying it edits system
firewall configuration.

**Options.**

- **(a) Ask, default yes.**
  - Interactive: "Allow nodes and phones on 10.0.0.0/24 to reach jarvisd? [Y/n]", then
    `sudo jarvisd doctor --fix`.
  - Non-interactive: apply only with `--yes`, otherwise print the command.
  - Only private LAN subnets, never `0.0.0.0/0`; rules tagged `jarvisd` so uninstall removes them.
- **(b) Always apply.**
- **(c) Print only**, as today.

**Recommendation: (a).** It fixes the most common fresh-install failure without surprising anyone, and
the admin's Check step still shows the command for anyone who said no.

### IQ6 [scope] Cutover data: `import-legacy` for identity and user data, or a clean start for everything?

**Context.**

LD5 makes prod's **models and LLM settings** start clean. It does not cover user data. Without an import:
every family member re-creates an account and re-joins a household, every node is factory-reset and
re-provisioned (and a reset wipes the node's Wi-Fi, STATUS finding 5), every phone re-pairs, and
memories, routines, phonebook and inbox are lost. PLAN §5 calls `import-legacy` "wanted, not required",
and the per-table plan exists (`docs/schema/cc.md:94-120` and the other `docs/schema` notes). The import
also copies both legacy JWT keys so sessions survive (decision log 2026-10-06).

**Options.**

- **(a) Import identity and user data, not models.**
  - `jarvisd import-legacy --from postgres://… [--dry-run]` runs on an empty home before the first start.
  - Users, households, nodes and keys, memories (re-embedded), routines, active schedules, phonebook,
    inbox, rooms and devices, blobs.
  - LLM settings skipped (LD5); the wizard skips Account (a superuser exists) and runs Models as on a
    fresh install, so the pain LD5 wants to see is still seen.
- **(b) Start clean**: re-create accounts, re-provision every node.
- **(c) (a) for prod only**, not offered to other legacy users.

**Recommendation: (a), offered to everyone on the legacy stack.** Nodes and phones keep working because
the host and ports are unchanged; the legacy databases are only read, so rolling back to legacy stays
possible.

### IQ7 [behaviour] A legacy stack on the same box

**Context.**

jarvisd uses the legacy ports by design: 7700–7707, 7712, 7030, 7031, 7710, and MQTT 1884/9883, which
legacy mosquitto also publishes. It binds every listener before serving, so a single clash stops it
from starting at all (`internal/platform/module/runner.go:105-108`). Prod today listens on 7710 and 7711
(legacy admin).

**Options.**

- **(a) Detect and refuse, offering `--stop-legacy`.**
  - Detection: `jarvis-*` containers, `~/.jarvis/compose` or `tokens.env`, and ports held by other
    programs.
  - `--stop-legacy` runs `docker compose stop` and turns off the restart policy. It never runs `down -v`.
  - Print the `import-legacy` command.
- **(b) Side by side on alternate ports.** Nodes and phones only ever find one config service per host,
  so this is a developer setup, not a user one.
- **(c) Remove legacy** (`down`, delete volumes).

**Recommendation: (a).** Developers keep using `JARVIS_PORT_*` by hand. Rolling back is
`jarvisd service stop` plus `docker compose start`.

### IQ8 [behaviour] Push relay: on by default?

**Context.**

`RELAY_URL` unset means push delivery is disabled and sends are only logged
(`internal/modules/notifications/notifications.go:99-101`). The legacy installer defaulted it to
`https://relay.jarvisautomation.io` (`jarvis-admin/server/src/services/generators/env-generator.ts:99`).
With it set, each push (title and body) leaves the house through the project's relay to Expo. The core
principle is "no cloud dependencies by default", but a phone that never gets a notification looks broken.

**Options.**

- **(a) Opt-in in the wizard's Done step**, explaining exactly what leaves the box. Stored as a setting
  `notifications.relay_url` with `RELAY_URL` as the env fallback. The admin shows "push notifications
  off" until it is on.
- **(b) On by default**, as the legacy installer did.
- **(c) Env only**, as today.

**Recommendation: (a).** Private by default, one click to enable, and nobody wonders why pushes don't
arrive.

### IQ9 [scope] Code signing: Apple notarization and Windows Authenticode now?

**Context.**

The one-liners avoid most friction: `curl` sets no quarantine flag and the Go linker ad-hoc signs
darwin/arm64; `Invoke-WebRequest` adds no Mark-of-the-Web and the script runs `Unblock-File`. A **browser**
download is a different story: Gatekeeper blocks the unsigned binary on macOS, SmartScreen warns on
Windows, and Defender is likelier to flag the extracted DLLs and downloaded engines. Signing costs an
Apple Developer account (yearly fee) and a Windows code-signing certificate, plus key custody in CI.

minisign is separate and cheap: the project key already exists and signs node and admin releases
(`jarvis-node-setup/install.sh:480-491`).

**Options.**

- **(a) Phase 6 ships the one-liners only**, with SHA256 verification and minisign-signed checksums.
  Add notarization and Authenticode when friends and family start downloading from a browser.
- **(b) Sign and notarize from the first release.**
- **(c) Never sign**; document the `xattr` and "More info → Run anyway" steps.

**Recommendation: (a).**

### IQ10 [behaviour] Upgrade safety

**Context.**

goose runs migrations at start, forward-only, out-of-order allowed (`internal/platform/db/migrate.go:30`).
A bad release can migrate the DB and then crash-loop. What an older binary does with a DB that has
migrations it doesn't know is unverified. Node-setup already has a health-gated rollback
(`jarvis-node-setup/install.sh:1905-1983`).

**Options.**

- **(a) Re-running the installer upgrades, with safety:**
  - a `VACUUM INTO` snapshot before the upgrade, keeping 3;
  - the previous binary kept as `jarvisd.prev`;
  - a health gate (`/health`, stable supervisor, doctor listeners) with an automatic rollback, restoring
    the snapshot only when migrations ran;
  - a downgrade guard: jarvisd refuses to start on a DB migrated by a newer version.
- **(b) Plain replace**, with manual recovery.

**Recommendation: (a).** Prod is the user's home instance and tolerates outages, but not lost data.

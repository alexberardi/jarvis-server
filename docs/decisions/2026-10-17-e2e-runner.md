# The E2E runner: scripts/e2e, Playwright Test, one sandbox per run

- **Date:** 2026-10-17 (user asked for automated E2E regression of the admin web app and the
  mobile app on a manual trigger; design by agent, loop item #142, piece 2/9)

`scripts/e2e [web|mobile|all] [--filter RE] [--keep]` is the one entry point for the E2E
suites. How to run it and the report's schema: [`../dev/e2e.md`](../dev/e2e.md).

- **Its own sandboxes, every run.** A run brings up a fresh, uniquely named sandbox
  (`--profile rich --llm scripted --ui`, from the checkout under test) and purges it afterwards,
  so a run never depends on a sandbox someone else left in some state, and two runs (or a run
  and an agent's own sandbox) never share data. `--keep` is for poking at a failure.
- **An empty sandbox for first-run setup.** `scripts/sandbox up --profile empty` skips
  seed-dev.py, so no superuser exists and the setup token is still valid; `sandbox.env` exports
  `SBX_SETUP_TOKEN` and no logins. The wizard test runs on that second sandbox (`<name>-setup`)
  and skips every model step, so it downloads nothing.
- **Playwright Test (TypeScript), not more of tools/screenshots.** The suites need fixtures,
  per-role storage state, screenshots and traces on failure, and a
  reporter; Playwright Test has them. It is pinned to the Playwright version tools/screenshots
  uses so both share one cached Chromium. The login form is filled by one shared function,
  `tools/screenshots/signin.mjs`, used by both.
- **Behaviour, not page loads.** Each test checks what changed on the server through the
  sandbox's APIs (a memory saved, an inbox item read or gone, a node signed out, a session
  revoked) as well as what the page shows. Tests that change something use throwaway users
  in households of their own, so test order does not matter.
- **One worker.** The suite shares one sandbox, one active model script and the auth module's
  per-IP rate limit (30 logins/registrations/refreshes a minute, not configurable). Seeded roles
  sign in once (global setup); throwaway users start from their registration's session.
- **report.json is an interface.** The loop's trigger (E2E 9/9) and the coverage gate (8/9)
  read it, so it is versioned (`schema: 1`) and only grows. Each suite writes its own
  `results.json` in one record shape and `scripts/lib/e2e_report.py` merges them, so the mobile
  suite (4/9) plugs in without touching the web suite. A suite that cannot run is reported
  (`status: error`) rather than leaving no report.

Found by the first runs and fixed with it: signing out right after the setup wizard showed a
blank page (the boot gate's "needs a superuser" flag was never cleared, so `/login` and `/setup`
redirected to each other), and opening an inbox item left the sidebar's unread badge stale
(the server's GET marks the item read, so the page never refreshed the count).

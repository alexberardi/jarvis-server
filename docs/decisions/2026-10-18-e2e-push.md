## Every run: the fake relay

- **Every sandbox has one, not only the E2E ones.** `scripts/sandbox up` starts `tools/fakerelay`
  and passes it to jarvisd as `RELAY_URL`, the env fallback of the `relay.url` setting, so it
  holds before seeding and on `--profile empty` too, and a test may still set the setting. A
  sandbox never reaches the real relay unless asked (`--relay URL`); `--relay none` gives an
  install without push. Before this, sandboxes had no relay and every push was logged
  `skipped`, so no test could see one.
- **It speaks the relay's protocol, nothing more:** `/v1/register` gives a JWT per household
  (random per process, so a restarted relay refuses cached ones and jarvisd's re-register path
  runs), `/v1/send` refuses a wrong or missing JWT with 401 and answers one result per token.
  `fail:*` tokens answer `DeviceNotRegistered`, which makes jarvisd deactivate them.
  `/control/pushes` (filters `token`, `household_id`, `title`) is what tests read;
  `/control/fail` fails the next sends with a status. The contract suite keeps its own
  in-test fake (`contract/notifications_relay_test.go`), which freezes the wire format against
  legacy; this one is a harness server.
- **Tests assert on the push, not on the log row.** A web test gives a throwaway user a fake
  Expo token (`POST /api/v0/tokens`, as the app does), makes the event happen and waits for the
  push with that token and a unique title (the server drops an identical push within 60 s). It
  checks title, body, `data.type`, `data.inbox_item_id`, priority and the target tokens. A
  test fails when `relay.url` is not the fake relay (checked: all of `push.spec.ts` fails on a
  `--relay none` sandbox).

### The events that send a push, and what covers them

Every push goes through `notifications.Notify`; the cc events reach it through
`postInboxItemWith`/`pushConfirmation`/`sendLinkPush` (some through `notifyGated`, the attention
broker, off by default per household).

| event | where | E2E |
|---|---|---|
| a node's inbox item with a push: timers, reminders, alerts, any category | `cc/nodeplugin.go` `/node/inbox-item` | `push.spec.ts` (timer, reminder, alert; household target; no push when not asked) |
| a node's push (a confirmation card) | `/node/push-notification` | `push.spec.ts` |
| send_link | `/node/send-link` | `push.spec.ts` |
| a service's notify and notify batch (deep research, recipes and other apps) | notifications `/api/v0/notify`, `/notify/batch` | `push.spec.ts` |
| watch alert | `cc/watches_fire.go` | `push.spec.ts`: a chat turn as the user, where the scripted model (`e2e/llm/web.json`) calls `create_watch` on `appt.upcoming`, then the node posts that signal (`POST /api/v0/signals`); the `watch_alert` push to the user's phone, and its inbox item. Web-page watches: Go tests (`watches_fire_test.go`) |
| errand step or checkpoint | `cc/errands.go` | not yet: needs an errand run by the model; Go tests |
| automation that ran on its own | `cc/signals_reactions.go` | not yet: needs a signal automation, a node command and an Allow rule; Go tests |
| phone call cards | `cc/phone/cards.go` | not yet: needs a phone call; Go tests |
| deep research done | `cc/servertools/deepresearch.go` | not yet end to end (the push itself is the notify path above); Go tests |
| recipe photo import done | `recipes/photo_chat.go` | not yet; Go tests |
| routine finished (household) | `cc/routines_run.go` | not yet: run-now waits for a connected node's result (90 s timeout without one); Go tests |
| proposals, automation confirmations | `cc/proposals.go` | not yet: made by the model; Go tests |
| schedule lists | `cc/schedules.go` | not yet: made by the model; Go tests |
| a node command's callback card, when it asks for a push | `cc/callbacks.go` | not yet; Go tests ("couldn't reach" cards never push) |
| a voice command waiting for confirmation | `cc/voice_routes.go` (`pushConfirmation`) | not yet: needs a voice turn; Go tests |
| attention journal | `cc/attention.go` | inbox only, never a push |

The rows marked "not yet" share the path the covered events prove (inbox item → `Notify` →
queued job → relay); what an E2E test would add is the event's own trigger. Each needs the
scripted model to drive a tool (`e2e/llm/`) and is a follow-up.

- **Mobile, every run.** The harness emulator (`google_apis`) has no Play services, so the app
  gets no FCM token there. `scripts/e2e mobile` registers a fake token for the superuser and
  hands the flows `FAKE_RELAY`, `PUSH_TOKEN`, `CC_URL`, `NODE_API_KEY` (the seeded node) and
  `USER_ID`; a flow asserts from a `runScript` (it runs on the host, where the fake relay is).
  The push flows themselves are a jarvis-node-mobile item, as the other flows are.

## Overnight: real FCM (`scripts/e2e mobile --real-push`)

- **One test, its own suite (`mobile-push`), instead of the flows.** Overnight runs `scripts/e2e
  all` and then `scripts/e2e mobile --real-push`; the flows never run against a real relay.
- **Its own AVD, `jarvis-harness-play`,** on the newest `google_apis_playstore` x86_64 image:
  FCM needs Play services. The default AVD and its image are untouched. No Google account is
  signed in.
- **The APK is built with the push config:** `E2E_PUSH_GOOGLE_SERVICES` (the
  `google-services.json`) is copied into the build as `./google-services.json` and named in
  `$GOOGLE_SERVICES_JSON`. The app config must point `android.googleServicesFile` at one of
  them; the build checks that prebuild put it into the native project and stops otherwise. The
  APK is cached by the commit and the file's hash. The Expo project's FCM credentials (the
  service account key uploaded to Expo) must match that Firebase project; that is Expo's side
  and not checked here.
- **The test** (`tools/e2emobile realpush`): sign in with the mobile repo's own login subflow
  (`.maestro/subflows/login.yaml`, else `.maestro/login.yaml`); wait up to 2 minutes for the
  app to register a token (`/api/v0/tokens/me`) that was not there before the sign-in (the lane
  also purges its sandbox first, so an earlier `--keep` run's fake token cannot pass this step); press Home; post a node alert with a push to
  the user; expand the shade and look for the title in `uiautomator dump` for up to 3 minutes;
  tap its centre; expect the title on screen in `com.jarvis.nodemobile` within 30 s. Each
  failure says which step, and keeps the screen, the dump and logcat.
- **Skipped, with the reason in the report, when:** `E2E_REAL_RELAY_URL` is unset or not an
  http(s) URL; `E2E_PUSH_GOOGLE_SERVICES` is unset or unreadable; there is no Google Play image;
  the relay does not answer at all (a `POST /v1/register` with no household, which it refuses
  without registering anything). The two variables come from the environment or
  `~/.config/jarvis-harness/push.env` (`$JARVIS_HARNESS_PUSH_ENV`), never from the repo. A
  skipped lane leaves the run green, so the overnight report has to be read for "skipped".
- **What was not checked when this was built:** the lane past its skips. The build sandbox had
  no Play image, no push config and no mobile checkout; the steps are unit-tested against a fake
  adb, Maestro and sandbox (`tools/e2emobile/realpush_test.go`). The first real run is the
  user's, with the relay URL and the `google-services.json`.

# The iOS lane: the mobile E2E flows on the iOS Simulator, against a LAN sandbox

- **Date:** 2026-10-18 (user: the ask of loop item #155, E2E piece 13; the split between the
  machines and the rest by agent)

`scripts/e2e ios` plays the same Maestro flows as `scripts/e2e mobile`
([`2026-10-18-e2e-mobile-runner.md`](2026-10-18-e2e-mobile-runner.md)) on the iOS Simulator of
the MacBook Pro (`<mbp-host>`: Xcode 26.3, the iOS 18.0 and 26.1 runtimes). How to run it:
[`../dev/e2e.md`](../dev/e2e.md).

## Who runs what

- **The sandbox runs on the Mac (2026-10-21, #451); the dev box is the alternative.** #155's
  QA on the MacBook Pro found the dev box's ufw admits only the installed jarvisd's ports, so
  the Mac could not reach a dev-box sandbox. `scripts/sandbox` now runs on macOS too (no
  `setsid`, `ss` or `ip` there), so the Mac brings the `--lan` sandbox up itself; a dev-box
  sandbox needs its ports opened to the Mac for the run (`../dev/e2e.md`). The original split
  follows.
- **The sandbox runs on the dev box (user); the suite runs on the Mac.** The dev box brings up
  `scripts/sandbox up --name <n> --profile rich --llm scripted --lan`; the Mac runs
  `scripts/e2e ios --sandbox-env <copy of .sandbox/<n>/sandbox-lan.env>`. The suite neither
  starts nor stops that sandbox; whoever brought it up takes it down (`down --purge`) after the
  run. One script driving both machines over ssh was the other option; it was not taken
  because the loop's runners (and its agents' sandboxes) cannot ssh between the machines, and
  the Mac runner is where the ask puts the run.
- **The Mac runner gets the capability `ios`** (#94's runner on the MacBook Pro), so the loop
  sends iOS runs there. That runner's config is the user's, on the Mac, and the capability is
  set in jarvis-loop, not here; a loop job that brings the dev box's sandbox up, hands its
  `sandbox-lan.env` to the Mac runner and purges it afterwards is jarvis-loop's to build.
- **The Mac mini is not a fallback today:** it has the command-line tools only, which have no
  simulator (`scripts/e2e ios` says so and stops). Installing Xcode there (and the iOS 18.0
  runtime) makes it one; it then creates its own `jarvis-harness-e2e` device, as any Mac does.

## How the simulator reaches the sandbox

- **`scripts/sandbox up --lan`** binds jarvisd (`JARVIS_HOST=0.0.0.0`), the scripted model's
  control API (so the Mac can switch scripts) and the fake push relay (so a flow's `runScript`
  on the Mac can read `FAKE_RELAY/control/pushes`) to every interface; MQTT listens on every
  interface anyway. The model tap stays on loopback, since only jarvisd calls it. The LAN address
  (the default route's source address, or `$JARVIS_LAN_HOST`) goes into `sandbox.env` as
  `SBX_LAN_HOST` and `SBX_LAN_CONFIG`, and `sandbox-lan.env` is `sandbox.env` with every
  `127.0.0.1` URL on that address, less `SBX_LLM_TAP`: every URL in it answers from the Mac.
- **No tunnels.** The simulator shares the Mac's network, and jarvisd registers its own
  listeners with host `localhost`, which the config service rewrites to the address the app
  asked it on. An app whose config URL is the dev box's LAN address therefore gets every other
  service on that address too. (Forwarding every port with `ssh -R`, as adb reverse does on
  Android, was the alternative; it needs ssh between the machines.) So the Android runner's
  per-flow device check and retry on an adb transport drop (`retryOnDrop`, `--reverse`,
  `--health-port`) does not apply: on iOS each flow runs once, as is. After a failed flow the
  runner reboots the simulator before the next (#451): a SpringBoard alert a flow leaves up
  survives `launchApp` with `clearState`, and it failed every later flow of #155's QA run.
- **A `--lan` sandbox shows its seeded logins (`DevPass123!`), admin key and auth admin token
  to the LAN** for as long as it is up. It is a throwaway household on a home LAN; take it down
  after the run, and never use `--lan` on a sandbox holding anything real.

## The app and the device

- **The build:** a `git archive` of the mobile commit (as the APK), `expo prebuild --platform
  ios --clean`, `pod install`, then `xcodebuild` Release for `iphonesimulator`, the Mac's arch
  only, with `CODE_SIGNING_ALLOWED=NO`: no team, no certificates, nothing of the user's. Same
  env as the APK (`EXPO_PUBLIC_DEV_MODE=true`), but the config URL baked in is the sandbox's LAN
  one (`EXPO_PUBLIC_MANUAL_CONFIG_URL=$SBX_CONFIG`), so the cache key is the mobile commit and
  that URL: `~/.cache/jarvis-harness/mobile/ios/app/jarvis-mobile-<sha>-<url hash>-r<recipe>.app`.
  A sandbox on the same offset and address reuses the build.
- **The simulator is the harness's own:** `jarvis-harness-e2e` (iPhone 16, iOS 18.0; override
  with `E2E_IOS_DEVICE_TYPE` and `E2E_IOS_RUNTIME`), created once with `simctl create`, its UDID
  kept in `~/.cache/jarvis-harness/mobile/ios/simulator.udid`. Each run erases it, boots it
  headless, freezes the status bar at 9:41, installs the app, and shuts it down afterwards.
  **Every simctl call names that UDID**, never `booted`; `tools/e2emobile --platform ios`
  refuses a UDID simctl does not list under that name, so the user's simulators are never
  touched. One run at a time per device (a lock in the cache).
- **Maestro** is the same pinned 2.11.0 (a JVM zip, same sha256), with `--device <udid>`.

## The report

- The suite is `ios` in `report.json` (records of the same shape as `mobile`), with each flow's
  files in `.e2e/<run>/ios/<flow>/`. On a failure: `screenshot.png` (`simctl io screenshot`),
  `hierarchy.json` (`maestro hierarchy`: texts and accessibility ids), `device.log` (the app's
  process in the simulator's log since the flow started, `log show --style compact`) in place
  of the logcat, and `console_errors` are its error- and fault-level React Native
  (`com.facebook.react.log`) lines. `all` does not include `ios`: it needs a Mac.

## Additions to the flow contract (jarvis-node-mobile's `.maestro/`)

- **Platform differences go in the flow, not in a copy of it:** Maestro's conditions,
  `runFlow: {when: {platform: iOS}, commands: [...]}` (or `Android`), around the steps that
  differ. Every flow runs on both platforms unless tagged `skip`.
- **The same environment on both platforms:** `scripts/e2e`'s `flow_env` builds the `-e` set
  for both suites (EMAIL\*, PASSWORD, CHAT_MESSAGE/CHAT_REPLY, and #269's FAKE_RELAY,
  PUSH_TOKEN, CC_URL, NODE_API_KEY and USER_ID, with the superuser's fake token registered as an
  `ios` device here); the iOS suite adds only `PUSH_URL`.
- **Push on iOS:** every flow gets `PUSH_URL`. A `runScript` that POSTs an APNs JSON payload
  there (`http.post(PUSH_URL, {body: JSON.stringify({aps: {alert: {title: "…", body: "…"}}, …})})`)
  has it delivered to the app with `xcrun simctl push <udid> com.jarvis.nodemobile`; the flow
  then taps the banner and checks where it lands. The payload's app-specific keys are whatever
  the app's notification handler reads. Android's push path is the fake relay of #150; flows
  put the iOS delivery step under `when: platform: iOS`.
- **How `PUSH_URL` fits #269's push design** ([`2026-10-18-e2e-push.md`](2026-10-18-e2e-push.md)):
  the fake relay records what jarvisd sends and nothing reaches a device, on either platform;
  the real-push lane (`--real-push`, real FCM) is Android-only. `PUSH_URL` is the iOS half of
  delivery+tap: a flow makes the event happen, reads the recorded push from
  `FAKE_RELAY/control/pushes?token=PUSH_TOKEN` (which checks that jarvisd sent the right one),
  and posts that push's title, body and data as an APNs payload to `PUSH_URL`, so the
  simulator shows it and the flow can tap it. It tests the app's handling of a push, not
  APNs; there is no real-APNs lane.
